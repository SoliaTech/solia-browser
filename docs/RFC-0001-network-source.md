# Solia Browser RFC 0001 · 从 URL 打开 Solia 应用

| 项目 | 内容 |
| --- | --- |
| 状态 | 设计草案 |
| 范围 | 首个可交互的桌面 MVP，单窗口、单实例 |
| 涉及仓库 | SoliaTech/solia-browser、SoliaTech/solia |

## 1. 首次使用

用户在地址栏输入指向 `.solia` 源文件的 HTTPS 直链，按回车。Browser 下载源码，在本机编译，然后在地址栏下方显示应用。以现有 Counter 为例，首次显示 **Count: 0**，点击 **Increment** 后显示 **Count: 1**。发布者只需提供能返回源码的静态文件地址。

首个里程碑覆盖 README 第 3 节中的源码 URL 流程。本地开发也走网络加载路径，可通过回环 HTTP 服务直接提供仓库里的示例。后续里程碑再加入远程预编译包、本地文件选择、持久缓存和多标签。[项目说明](../README.md#3-core-user-experience)

## 2. 从下载到渲染

| 阶段 | 负责方 | 输入与产物 |
| --- | --- | --- |
| 导航 | Browser | 地址栏提交 URL，记录本次导航编号，显示加载状态 |
| 获取源码 | Browser | 后台 GET，校验响应，解码 UTF-8，保留最终 URL 作为诊断来源 |
| 编译与实例化 | Solia | 复用前端做词法、语法和类型检查，生成内存中的 SAPP v1，再交给已有加载器创建独立的 WASM 实例 |
| 显示与交互 | Browser + Solia | Browser 提供窗口和内容区；Solia 绘制控件、执行按钮处理器、按新状态重绘 |

源文件服务只传输文本。从 URL 获取源码是 Browser 的操作，应用本身继续在空导入环境中运行。无需把下载的源码或中间包写入磁盘。

## 3. 两个仓库的接口

依赖方向为 `solia-browser → solia`。Solia 当前的 CLI 把创建窗口与运行应用绑在一起，Host 还负责创建根面板。建议在同一 Cargo 包中新增库入口，从现有代码中提取以下接口，让 CLI 和 Browser 共同使用。

```rust
// 建议接口
pub fn compile_source(source: &str) -> Result<Vec<u8>, CompileError>;

impl AppInstance {
    pub fn from_package(bytes: &[u8]) -> Result<Self, LoadError>;
    pub fn render(&mut self, ui: &mut egui::Ui) -> Result<(), RuntimeError>;
}
```

编译错误保留原始行列号，由调用方加上文件名或最终 URL。应用主题和布局仅作用于传入的内容区；宿主继续使用当前 wasmi 实现与处理器执行预算。Browser 管理窗口、URL、HTTP 客户端、加载状态和导航错误。双方使用同一 egui 版本。

两个工作树先通过 `solia = { path = "../solia" }` 联调。独立构建时，将共享库提交到可访问的 Solia 私有仓库，Browser 固定到该 Git 提交并保留 Cargo.lock。

## 4. 网络加载约定

- **地址。** 首版接受路径以 `.solia` 结尾的直接 HTTPS URL，允许查询参数。开发环境也接受 `http://localhost` 与回环 IP 上的 HTTP。使用默认 TLS 证书校验。访问私有仓库的登录页会产生加载错误；联调可直接通过本地 HTTP 服务提供示例。
- **重定向。** 最多跟随 3 次，每一跳重新验证协议与目标。HTTPS 链禁止降级为 HTTP；回环 HTTP 开发请求保持在回环地址。最终地址显示为正在运行应用的来源。
- **响应。** 预期完整的 HTTP 200 响应。接受 `text/plain`、暂定的 Solia 源码媒体类型，以及静态服务器常用的 `application/octet-stream` 或缺省类型；HTML 等明确冲突的类型给出错误。最终内容必须通过 UTF-8 解码和 Solia 编译。
- **资源限制。** 建议首版每次导航的网络总时限为 15 秒（含重定向），解码后的响应体上限为 1 MiB。流式累计实际字节数，即便响应缺少长度头也执行同一限制。

## 5. 重载与失败恢复

下载、编译和候选实例准备在后台完成。用户输入新地址时，取消前一次下载；已进入编译阶段的旧结果按导航编号丢弃。对任务数设上限，只保留最新待处理请求。准备成功后，在 UI 线程替换实例并更新当前应用地址。

重载重新请求用户上次成功提交的 URL，读取服务端当前源码并从初值启动。请求失败或编译出错时，显示失败阶段、目标地址及原因；编译错误附行列。若已有应用，保留其计数和交互，直到新应用成功就绪。首次打开失败时，地址栏仍可修改和重试。运行时错误呈现在内容区。

## 6. 实施顺序与验收

1. **打通共享渲染。** 在 Solia 提取库入口，保持 CLI 行为。现有 Counter 回归测试通过；两个独立实例互不影响。
2. **打通网络源码。** 在 Browser 增加原生窗口、地址栏和后台下载。开发者从包含两个仓库的父目录运行下列命令，在地址栏打开 `http://127.0.0.1:8080/counter.solia`，点击按钮后在同一窗口看到计数增加。
3. **验证真实 HTTPS。** 将相同文件放在可访问的 HTTPS 静态服务，使用直链完成同样的交互。修改服务端标签后重载，验收新标签和重置后的计数。
4. **验证恢复路径。** 使用本地测试服务覆盖 404、HTML 响应、超限、超时和非法重定向；用错误源码验证行列诊断。测试先打开慢地址 A、再打开快地址 B，最终只展示 B。分别记录三个目标桌面平台的实测情况。

```sh
python3 -m http.server 8080 --bind 127.0.0.1 --directory solia/examples
```
